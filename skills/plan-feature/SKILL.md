# /cc-code:plan-feature — 增量需求规划编排器（第一动作即 plan 模式）

> ⭐⭐⭐ **触发后第一动作 = call `EnterPlanMode` 工具。**
> ⚙️ 引擎分支（双端同一条规则）：无 `EnterPlanMode` 工具的引擎（如 Codex）→ 第一动作改跑 Bash `mkdir -p .cc_code/.runtime && touch .cc_code/.runtime/plan-lock` 开护栏（此后写盘被 gate.sh 拦）。**一次批准窗口只解锁一次**：每个「主人批准」之后 `rm .cc_code/.runtime/plan-lock`，把这一批该落的全部落完（批准一：先 pm 落 prd、再 uiux 落 ux / design 构图；批准二：冲突修订先落 prd / ux，再落 L3），落完立刻 `touch` 回锁；进入技术阶段前保持锁定。
> **适用场景：MVP 已交付，在既有实现上做功能迭代。** 0→1 定全量请用 `/cc-code:plan-mvp`。
> **本命令的主控只是传话员**：问需求、判冲突的是 `pm` agent；问页面、布局与已锁视觉规格的是 `uiux` agent；读代码、算爆炸半径、问技术的是 `architect` agent。主控不读代码、不读技术文档、不跑 codegraph、不思考需求、不替主人回答。
> **主人批准两次**：需求与原型一次、技术方案一次。批准即定稿，落盘后无二次验收。

## ⛔ 六条铁律（违反任一即本次规划无效）

### 铁律 1：第一动作 call EnterPlanMode
触发后，在 call `EnterPlanMode` 之前，**不许做任何动作**：

- ❌ 不许先 Read 任何文件
- ❌ 不许先派 agent
- ❌ 不许先输出任何内容
- ✅ 唯一允许的第一动作：call `EnterPlanMode` 工具

### 铁律 2：主控只传话，不扮演任何角色
主控能做 / 不能做的清单单一出处 = `active/Agent.md` §一、§五，本命令不复述。本命令只加一条：体检（Step0.5）主控只看目录与规范形态，不读内容；codegraph 侦察归 architect。**两处例外**：体检可读 `active/Agent.md` 判断宪法版本（只为判版本形态，不是 `src/`、不是 L3）；风格门可读 `active/status.md`「风格：」行（该行缺失时才回退读 `active/design.md` §0 状态行；只读状态，不读数值与内容）。

### 铁律 3：codegraph 只准校准 L3，永不许生成 L1 / L2 / L4
本命令最易踩的坑 —— **迭代场景下代码已存在，会本能地「读代码推需求」，那是需求层被实现层反向污染**。谁能用 codegraph、产出能流向哪里，单一出处 = `active/Agent.md` codegraph 权限矩阵，本命令不复述。本命令的落点：codegraph 只由 architect 使用；新需求的逻辑只能从【pm 与主人的对话】长出来，页面与原型只能从【uiux 与主人的对话】长出来。

> 结构上的保证：pm 全程不接触代码；代码事实只能以「业务语言的冲突描述」经主控原样问主人，再由主人的话回到 pm，永远不会作为「需求建议」流向 pm。

### 铁律 4：契约漂移禁沉默
architect 撞出「代码 ≠ `active/api.md` / `active/data.md` 契约」时，**立即交回主控，逐条请主人二选一**：改代码回归契约 / 修契约并记录。禁止默默按代码算、也禁止默默按契约算。

### 铁律 5：禁批量决策清单，一次一个问题
⛔ 禁止「全量输出决策清单，可全量接受 / 逐项修订 / 否决某项」。
pm / uiux / architect 每轮只交回**一个**模糊点或**一条**冲突；主控不合并、不拆分、不追加。

### 铁律 6：禁塞单一文件，越权红线
⛔ 禁止把所有产出一股脑写进 `active/prd.md`。必须按内容性质路由到对应层的文件，**一层一文件一个 agent**（见「五、落盘路由表」）。

```
⛔ active/gates.md、active/bugs.md —— qa 唯一域，本命令绝不写
⛔ src/ 与测试目录                  —— dev 唯一域，本命令绝不写
⛔ active/Agent.md                  —— 插件规范文件（唯一写者 = init 脚本），本命令一个字不许动
⛔ active/design.md 已锁定后         —— 只能经 /cc-code:plan-uiux（模式二）改；本命令只在免门档补 §十 构图
✅ active/status.md                 —— 主控唯一落盘动作（坐标 / 卡点 / 下一步 / 「风格：」行）

每个 active 文件只有一个写者：pm → prd；uiux → ux / design；
architect → project / data / api；qa → gates / bugs；dev → src；
curator → references/（经验库）。任何阶段无例外：
主控绝不自己 Write / Edit 这些文件（含「顺手补一行」「体检后补救」「落到实际文件」），
要改一律派对应写者 agent。
```

> **视觉门两端同源**：本命令的批准条件 = 执行器的开工条件——按 `status.md`「风格：」行判（该行缺失时回退看 `design.md` §0）：「已定未实现」→ 先走 `agent-uiux`；「未锁」（无冷启动豁免）→ 本次涉及页面就停下先走 `plan-uiux`；「已锁」→ 放行；「纯后端」→ 放行并标视觉不适用。判据只在本命令 §三 与执行命令各写一次，⛔ 不各自另立。

## 二、冲突回流（architect → pm / uiux → architect）

architect 在技术阶段发现需求写不通（代码已有等价实现而 prd 当新增、契约冲突无法共存、选了「放弃 / 延后」需要改需求），**不许自行改需求**：

```
architect 交回「需求冲突」（只用业务语言，不带技术细节）
     ↓
主控原样问主人
     ↓
主人回答
     ↓
主人原话 ──原样──► 原来那个 pm（续接，保留全部记忆）
     ↓
pm 交回「修订摘要」（业务语言；规划模式下写不了盘，此时不改 prd / ux）
     ↓
修订涉及页面 / 布局 / 已锁视觉规格？
     ├─ 是 ──► 修订摘要原样续接给原来那个 uiux，uiux 交回页面与构图侧的修订摘要
     └─ 否 ──► 跳过 uiux
     ↓
主控把修订摘要原样续接给 architect，architect 以该摘要为准继续
     ↓
……批准二之后，才落盘：先续接 pm 落 prd、再续接 uiux 落 ux，最后 architect 落 L3
```

> 落盘顺序始终是先 pm 后 uiux 后 architect。若修订碰到已锁 `design.md` 的数值 / 组件 / 视觉母题 → 不在本命令落，走「回门档」转 `plan-uiux`（模式二）。

## 三、Step0.5 规范体检门与 architect 侦察分工

### 规范体检（主控做，只看形态）

以**插件规范为唯一标尺**，项目 `.cc_code/` 的形态不作为依据。

| 体检项 | 判据 | 命中时的动作 |
| --- | --- | --- |
| 目录形态 | `active/` 下 prd / ux / project / data / api / status 齐备 | 缺项 → ⛔ 停手（见下） |
| 宪法版本 | 项目 `active/Agent.md` 不再有「当前激活角色」字段，且角色条目齐全（pm / architect / dev / qa / uiux / curator） | 仍是旧版 → ⚠️ **只提醒主人自己跑 `/cc-code:init`**，不阻断，本次按插件规范推进；⛔ 主控不得代跑 init、不得为补救体检结果改任何 active 文件（`status.md` 仍只在 Step4 / Step10 按本命令写坐标） |
| 风格门 | 有前端（`active/ux.md` §一 有任一非「无前端」的端）且 `status.md`「风格：」≠ **已锁** | ⚠️ 只提醒不阻断（与执行器开工视觉门同源，status 优先）：本次需求涉及页面 → 按状态补门——`未锁` → 跑 `/cc-code:plan-uiux`；`已定未实现` → 跑 `/cc-code:agent-uiux`；`已锁` → 不提醒；纯后端需求 → 放行并标「视觉：不适用（纯后端）」。`status.md` 该行缺失 → 回退看 `active/design.md` §0；老项目无 `design.md` → 首次开工可走一次性冷启动豁免（由执行器发放、只用一次），建议先跑 `plan-uiux` 补锁 |

> 风格门只看 `status.md`「风格：」行（该行缺失时才回退看 `design.md` §0），⛔ 主控不读 `design.md` 内容、不判审美；「本次是否涉及页面」由 uiux 在 Step2.5 判（见第四节）。

提醒话术（命中即报，只报一次，不啰嗦；升级由主人自己触发，主控绝不顺手代劳）：

```
⚠️ 本项目 .cc_code 为旧版形态，缺 <项>。
   建议：/plugin update cc-code  →  请你自己重跑 /cc-code:init 升级
   本次规划仍按插件规范推进。
```

**目录形态偏离 → 停手**（防写坏文件）：

```
规范路径缺失（如无 active/ux.md、prd.md 不在 active/ 下、L3 三件缺项）
  ⛔ 停：「规范路径 <X> 不存在，请先跑 /cc-code:init 归正目录形态，
          否则增量章节会落错文件造成版本冲突。」
  → 仅当主人明示「就落 <实际文件>」才落——由对应写者 agent（pm / uiux / architect）落，主控不自己写；落完再提醒一次升级
```

### architect 代码侦察（技术阶段第一件事，主控不参与）

> 侦察哪几路、各回答什么、产出流向哪、索引新鲜度保险、`affected` 返回空的处置、契约漂移二选一的块格式，单一出处 = `agents/architect.md` 增量侦察一节；codegraph 权限与边界单一出处 = `active/Agent.md` codegraph 权限矩阵。本命令不复述，只守铁律 3：代码事实一个字都不许流向 L1 / L2 / L4。

## 四、需求判定与冲突源

### 需求逐点三态（pm 判业务侧，uiux 判页面侧，文档层）

每个需求点必须落进一格，**禁悬空、禁一点跨两格**（跨了就是需求点没拆够，先拆）。pm 只判自己读得到的 prd 侧（冲突源 1~5）；页面、布局与已锁视觉规格侧（冲突源 6 / 9）由 uiux 在 Step2.5 用同一套三态判。

```
┌──────────────┬─────────────────────────────────────────────┐
│ ✅ 文档已有   │ prd / ux / design 已有等价规则                 │
│              │ → 报「已有，位置 <文件 §小节>」，问主人是否改口径│
├──────────────┼─────────────────────────────────────────────┤
│ ⚪ 未覆盖无冲突│ 不与任何已验收断言 / 规则 / Out of Scope 抵触  │
│              │ → 直接进新增逻辑                             │
├──────────────┼─────────────────────────────────────────────┤
│ ⛔ 未覆盖有冲突│ 与下表冲突源任一抵触 → 押进冲突硬门控           │
└──────────────┴─────────────────────────────────────────────┘
```

> 「代码是否已实现」是代码事实，由 architect 在技术阶段补；与 prd 判定不一致时走冲突回流。

### 冲突源必扫九处，一处不许跳

| # | 冲突源 | 在哪查 | 层 | 谁扫 |
| --- | --- | --- | --- | --- |
| 1 | 已验收模块及其断言 | `active/prd.md` 模块清单状态列（✅ 已验收）+ §1.5 断言主表 | L1 | pm |
| 2 | 模块核心规则 R | `active/prd.md` 逐模块规格 | L1 | pm |
| 3 | 全局规则 G | `active/prd.md` 全局规则 | L1 | pm |
| 4 | 明确不做 | `active/prd.md` Out of Scope | L1 | pm |
| 5 | 已作废/已删功能 | `backup/retired/prd.md` 原文 —— ⛔ active 里不留作废条目 | L1 | pm |
| 6 | 交互五态与断点布局 | `active/ux.md` 五态矩阵、页面布局与断点变化 | L2 | uiux |
| 7 | 数据契约 | `active/data.md` interface ↔ DB 列 | L3 | architect |
| 8 | 接口契约 + 架构决策 | `active/api.md` / `active/project.md` Needs Decision | L3 | architect |
| 9 | 已锁视觉规格 | `active/design.md` §二~§八（数值、组件长相）、§十（页面构图） | L2 | uiux |

### 冲突硬门控（pm 摆 1~5，uiux 摆 6 / 9，architect 摆 7~8；一次一条，四选一）

**未拿到裁决禁止出本阶段。** 主控把下面这个块原样展示，不改一个字：

```
⛔ 冲突 n/N 待裁决
   旧：<来源文件 §章节> <旧值原文>
   新：<需求点>
   四选一：
    [1] 以新替旧 → 旧内容整行原文搬 backup/retired/<源文件名>.md + 注明被谁取代，绝不重排绝不复用
    [2] 新旧共存 → 必须给出可判真假的分支判据，模糊判据不算裁决
    [3] 放弃新需求 → 本条移出范围，写进 prd.md Out of Scope
    [4] 延后       → 写进 prd.md Out of Scope 小节并标「延后」，不进本次断言
```

> 技术阶段（冲突源 7~8）若主人选 [3] / [4]，等于改需求，走第二节冲突回流让 pm 改 prd。页面侧（冲突源 6 / 9）选 [3] / [4] 同理，由 uiux 的修订摘要回流 pm。

### 新页版式两档（本命令唯一出处）

新页（或改版页面）在 Step2.5 由 uiux 判档；判据只有一条：**是否引入已锁设计规格之外的新东西**。

| 档 | 条件 | 怎么办 |
| --- | --- | --- |
| **免门档** | 新页只用已锁数值、已锁组件、已知构图范式（只是补一页，不引入新的视觉母题） | uiux 直接补 `ux.md`（新页追加在页章末尾）与 `design.md` §十 构图；登记进本次改动范围（`backup/change-log.md` 一行 + `status.md` 点名 F-n），⛔ 不重走视觉门 |
| **回门档** | 引入新数值、新组件或新视觉母题（新色板 / 新字体 / 新圆角阴影阶 / 新组件长相 / 新构图母题） | ⛔ 主控停本命令的这部分：交回主人，转 `/cc-code:plan-uiux`（模式二）走「定了」；回来后再继续技术阶段 |

> 锁定后 `design.md` 只能经 `plan-uiux` 改；本命令在免门档只补 §十 构图，⛔ 不写任何视觉数值。换主风格 skill = 换方向 = 回门档。
