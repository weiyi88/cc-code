# /cc-code:plan-debug — bug 诊断编排器（不进 plan 模式，bugs.md 自动整理）

> ⭐ **不进 plan 模式，没有「批准方案」这道门。** 诊断是收集事实，不是做决定；plan 模式会让 qa 写不了文件，中途一断线记录就丢。所以 qa **复现一成功就写 B-n**，诊断每推进一步就地补全，记录不等主人批准。
> **定位：技术诊断编排器，不是需求规划器。** 与 `/cc-code:plan-feature` 的分界：那个处理「需求模糊」，本命令处理「需求明确但实现错了」—— bug 本身就是需求，期望行为要么主人说了、要么 prd.md 已有断言。
> **主控只传话**：主控是编排者，不扮演任何角色——不读 `src/`、不跑 codegraph、不思考根因、不替主人回答、不写 `bugs.md`。复现取证与 B-n 登记归 `qa`，根因与方案归 `dev`（只读，不改任何文件）。
> **配对**：本命令把 B-n 整理到 `待修复` 后，修复执行走 `/cc-code:agent-debug`（增量定位 B-n → dev 修 → qa 复测 → affected 精准回归）。

## ⛔ 五条铁律（违反任一即本次诊断无效）

### 铁律 1：期望行为唯一来源 = 主人原话 + 既有 A/U 断言
诊断时最容易犯的错就是拿实现当期望。

```
期望行为的合法出处：
  ✅ 主人在对话里的原话
  ✅ prd.md §1.5 的既有 A 断言
  ✅ ux.md §2.3 的既有 U 判定项

  ⛔ 绝不许从「代码现状」反推「所以期望应该是 X」
  ⛔ 绝不许从 codegraph / 日志产出反推期望 —— 它们只答「代码 / 运行时现在是什么样」
```

> 出处由 qa 定位并写进 B-n；dev 诊断时期望行为一律取自 qa 报告里的出处，不自己推。

### 铁律 2：只有四种情况停下交人（裁决门）
qa 把 B-n 的状态写成 `待裁决`，并用**业务语言写一句要主人回答的问题**（写进 B-n 的「待裁决」字段）；主控把这句话原样问主人，⛔ 主控不自己判、不自己改。除这四种，一律自动往下走，不问主人。

| 编号 | 命中情形 | 谁发现 | 主人裁决后，主控派谁 |
| :-- | :--- | :--- | :--- |
| ① | 根因是**契约**错（api / data / project 本身错） | qa（读 dev 诊断后） | `architect` 改 L3 对应小节 |
| ② | 根因是**需求**错（prd / ux 本身错） | qa（读 dev 诊断后） | `pm` 改 L1 / L2 对应小节 |
| ③ | prd / ux / api 里**找不到期望出处**，无法判定是不是 bug | qa（复现阶段） | 主人说「这是新需求」→ `pm` 补需求；主人说「不是 bug」→ qa 把条目原文搬 `backup/retired/bugs.md` 后从 active 移除 |
| ④ | **复现不了** | qa（复现阶段） | 主人补充信息 → 续接原 qa 重新复现 |

> **纯实现层的 bug**（契约和需求都没错，是代码没按它们做）**不需要主人批准方案**，状态直接到 `待修复`。
> 「深层 bug 牵涉多文件」**不是**停下的理由 —— 爆炸半径大小是事实问题，由 dev 沿调用链、qa 用 `affected` 算出。

### 铁律 3：落盘即时，四段告知只告知不落盘
落盘物仅两处：`bugs.md` 的 B-n 条目（qa 写，复现成功当场写、之后就地补全）+ `status.md` 一行指针（主控写）。dev 诊断报告里的四段告知（现象 / 根因 / 爆炸半径 / 修法）服务当轮对话告知，⛔ 本体不落盘（过程）；只有它的**结论**落进 B-n 对应字段（结果）。

### 铁律 4：B 编号独立序列
`bugs.md` 的 B-n 独立递增（qa 读已有最大号取下一个），**绝不复用 A/U 序列**（那两个永久稳定，bug 断言生命周期是天级）。条目修完由 qa 搬 retired，不占 active 篇幅。

### 铁律 5：越权红线
角色权限唯一出处：`active/Agent.md` §三（主控的写权限见 §一）。本命令不复述权限表，只补两条本命令特有的约束：

- `dev` 在本命令内**只读诊断**：不改 `src/`、不改测试、不写 `bugs.md`。plan 模式不再兜底，这一条靠主控任务说明明文约束（见下）。
- `architect` / `pm` 只在铁律 2 路由命中、主人裁决后才被派，各改自己的层。

## 一、生命周期总览

```
触发 /cc-code:plan-debug "<bug 描述>"（不进 plan 模式，无批准门）
  │
Step1 派 qa（全新上下文）复现 + 取证 + 定位期望出处
  │   qa 每轮交回「下一个问题（一次一个）」或「已复现」
  │   主控把问题原样展示给主人，主人原话原样续接给同一个 qa（SendMessage）
  │   ├─ 复现成功 + 找到期望出处 → qa 立即写 B-n
  │   │                            （状态 = 待诊断；现象 / 复现步骤 / 期望出处 / 日志证据 / 需加探针）
  │   ├─ 找不到期望出处（③）     → qa 写 B-n，状态 = 待裁决 + 一句业务语言问题 ─► 去 Step5
  │   └─ 复现不了（④）           → qa 写 B-n（未复现 + 已试步骤），状态 = 待裁决 + 一句问题 ─► 去 Step5
  │
Step2 派 dev（全新上下文，只读）诊断根因 + 方案
  │   主控把 B-n 里 qa 的报告原样转交 dev（原样转交不算夹带），任务说明写明「只读诊断，不改任何文件」
  │   dev 交回诊断报告：四段告知（现象 / 根因 / 爆炸半径 / 修法，全部业务语言）+ 一行技术备注（影响文件清单）
  │   dev 说不清根因 → 交回「还缺什么证据」→ 主控原样交 qa 补取证 → 回 Step2
  │
Step3 主控把 dev 报告原样转给同一个 qa
  │   qa 就地补 B-n 的 根因 / 爆炸半径 / 方案（修法）（爆炸半径里的回归测试面用 affected 补算）
  │   ├─ 根因是契约错（①）→ 状态 = 待裁决 + 一句业务语言问题 ─► 去 Step5
  │   ├─ 根因是需求错（②）→ 状态 = 待裁决 + 一句业务语言问题 ─► 去 Step5
  │   └─ 纯实现层         → 状态 = 待修复（无需主人批准）
  │
Step4 主控写 status.md「下一步」一行指针（业务语言）
  │   待修复 → 「B-n 待修复，走 /cc-code:agent-debug」，并提示主人敲 /cc-code:agent-debug
  │   qa 补完 B-n 后，主控把四段原样告知主人（爆炸半径里的回归测试面取自 qa 补进 B-n 的结果）
  │   （现象 / 根因 / 爆炸半径 / 修法；告知，不等批准）
  │
Step5（仅 ①~④ 命中时）主控把 qa 写的那句问题原样问主人，status.md 指针写「B-n 等你裁决」
      主人回答后：
      ├─ ① 契约错 ─► 派 architect 改 L3 ─┐
      ├─ ② 需求错 ─► 派 pm 改 prd / ux ──┤
      ├─ ③ 新需求 ─► 派 pm 补需求 ───────┤──► 续接原 qa 更新 B-n（删「待裁决」行，按新契约 / 新需求复核）
      │   ③ 不是 bug ─► qa 把条目原文搬 backup/retired/bugs.md，从 active 移除，本命令结束
      └─ ④ 复现不了 ─► 主人补充信息续接原 qa 重新复现 ─┘
                       更新后的状态：
                       ├─ 已有 dev 诊断（①②）→ 待修复；方案受新契约 / 新需求影响则主控再派 dev
                       │                        只读重估一次，报告原样转 qa 更新
                       └─ 还没诊断过（③④）  → 待诊断 → 回 Step2
```

### 主控写给 agent 的任务说明（格式固定）

| 只写 | 不写 |
| :--- | :--- |
| 读哪些文件（status、prd、ux、bugs.md、project.md §七 日志契约…） | 主控自己对 bug 的理解、猜测、根因 |

## 二、各 agent 的本轮任务

### Step1 · qa（复现 + 取证 + 期望出处 + 登记）

| 项 | 内容 |
| :--- | :--- |
| 读 | status、prd、ux、bugs.md、project.md §七 日志契约、与现象直接相关的运行入口 |
| 问（一次一个） | 现象是什么 / 怎么复现（不可复现 → 陪主人定位触发条件）/ 期望行为是什么（出处：主人原话 or 既有 A/U 断言号）/ 何时开始出现 |
| 做 | 实际复现；按 `project.md` §七 取运行时证据（按 `requestId` / `level` / `route` 过滤，⛔ 不整文件读入）；项目无日志基建 → 「日志证据」写「无基建」 |
| 写 | **复现成功当场**写 B-n（字段与状态含义以 `templates/bugs.md` 为准），状态 = 待诊断；命中铁律 2 ③④ 则状态 = 待裁决并写那句问题 |
| 交回 | 已写入的 B-n 号 + 状态；需要主人回答的问题（一次一个） |

### Step2 · dev（只读诊断）

| 项 | 内容 |
| :--- | :--- |
| 读 | status、prd / ux（仅期望出处命中的断言与判定项）、project、data / api（仅命中小节）、qa 报告 |
| 做 | 顺着代码调用链查根因；算爆炸半径（沿 import / 调用图，只取事实，再翻成「影响哪些功能 / 页面」）；定修法（不动契约；动契约 / 动需求 → 在报告里如实写明，交回主控） |
| 禁 | ⛔ 不改任何文件（含 `src/`、测试、`bugs.md`）；⛔ 不读 `gates.md`；⛔ 不从代码现状反推期望 |
| 交回 | 四段告知（见下）：现象 / 根因（一句话说得清；说不清不许硬编）/ 爆炸半径（业务语言；估算则注明）/ 修法；另附一行技术备注：影响文件清单 |

### Step3 · qa（补全 B-n + 判流向）

| 项 | 内容 |
| :--- | :--- |
| 读 | 主控原样转交的 dev 诊断报告、自己写的 B-n |
| 做 | 就地补 根因 / 爆炸半径 / 方案（修法）；用 `affected` 补算爆炸半径里的「修完要回归哪些测试」（dev 不负责）；判断根因是否落在契约（api / data / project）或需求（prd / ux）上 |
| 写 | 纯实现层 → 状态改 待修复；契约错 / 需求错 → 状态改 待裁决 + 一句业务语言问题（不改文档、不改断言） |
| 交回 | B-n 号 + 当前状态；补算出的回归测试面（供主控拼进四段告知）；如有，那句要主人回答的问题 |

## 三、四段告知规格（bug 版，dev 产出，主控原样告知主人；只告知，不是批准门）

全部业务语言，不带函数名、不带代码；一个 bug 一张表，四行。

| 段 | 写什么 | 例 |
| --- | --- | --- |
| 现象 | 用户看到了什么 | 连点两次登录，第二次起所有操作都提示未登录 |
| 根因 | 一句话因果 | 先发的登录请求后到，把新登录状态覆盖了 |
| 爆炸半径 | 影响哪些功能 / 页面；修完要回归哪些测试（测试面由 qa 用 affected 算出后补进来） | 影响登录页、个人中心、订单页的登录态；回归：登录、登录态保持、订单提交 |
| 修法 | 改哪里（业务层说法），会不会动到规则（契约 / 需求） | 提交期间锁住登录按钮，失败则回到未登录；不动契约、不动需求 |

```
四段告知的流向（只画逻辑）：

  dev 诊断报告（现象 / 根因 / 爆炸半径 / 修法）
        │
        ▼
  qa 补完 B-n（回归测试面补进「爆炸半径」）
        │
        ├──► 结论落进 B-n 对应字段（结果，落盘）
        │
        └──► 主控把四段原样告知主人（过程，不落盘，不等批准）
```

> 修法会动到契约或需求 → 不是纯实现层，走铁律 2 ①②，不在四段里替主人拍板。

## 四、落盘规格

### bugs.md 条目模板与状态

字段集与状态含义（待诊断 / 待裁决 / 待修复，各由谁置入）的单一出处 = `templates/bugs.md`（生成项目里的 `active/bugs.md` 头部），本命令不复述；qa 写，单条 ≤20 行。

### 落盘动作

| 序 | 时机 | 谁 | 文件 | 内容 |
| :-- | :--- | :--- | :--- | :--- |
| 1 | 复现成功当场 | `qa` | `active/bugs.md` | 新增 B-n（读已有最大 B 号取下一个），状态 = 待诊断 |
| 2 | 收到 dev 诊断后 | `qa` | `active/bugs.md` | 就地补 根因 / 爆炸半径 / 方案（修法），状态 = 待修复（或待裁决） |
| 3 | 命中铁律 2 任一情形 | `qa` | `active/bugs.md` | 状态 = 待裁决 + 「待裁决」字段写一句业务语言问题 |
| 4 | 主人裁决后（①②③ 需改文档时） | `architect` / `pm`，先于 qa 更新 | `active/api.md`·`data.md`·`project.md` / `active/prd.md`·`ux.md` | 按主人裁决改对应小节 |
| 5 | 裁决后 | `qa` | `active/bugs.md` | 更新 B-n、删「待裁决」行、改状态；判定不是 bug → 条目原文搬 `backup/retired/bugs.md` 再移除 |
| 6 | 每次状态变化后 | 主控 | `active/status.md` | 「下一步」一行指针（业务语言） |

⛔ 四段告知本体、复现与诊断过程、问诊记录**均不落盘**（B-n 只存结论；B-n 字段与四段一一对应：现象 / 根因 / 爆炸半径 / 修法（方案） / 状态）。

> ⭐ **落盘前必过「就地更新 + 搬运归档」**（规则单一出处 = `active/Agent.md` §四第 5 条）：各写者只改自己负责的文件；B-n 就地改字段，⛔ 不另起一条新的。

## 五、关键约束速查

| 约束 | 说明 |
| :--- | :--- |
| 不进 plan 模式 | 诊断是收集事实；记录不等批准，复现成功 qa 就写 B-n |
| 主控只传话 | 不读 src、不跑 codegraph、不想根因、不替主人答、不写 bugs.md |
| 期望唯一来源 | 主人原话 + 既有 A/U 断言；⛔ 禁 codegraph / 日志反推 |
| 只在四种情况停下 | ① 契约错 ② 需求错 ③ 找不到期望出处 ④ 复现不了；状态 = 待裁决，qa 写一句业务语言问题 |
| 纯实现层 | 不要主人批准方案，状态直接到 待修复 |
| subagent 不能问主人 | 所有问题交回主控，由主控交人 |
| 四段告知只告知不落盘 | 本体不落盘，结论进 B-n；落盘物仅 B-n 条目（qa 写）+ status 指针（主控写） |
| B 序列独立 | 不复用 A/U；修完由 qa 搬 retired |
| 不修不写码 | dev 只读诊断；本命令没有任何人写 `src/` |
| 权限单一出处 | 角色权限只在 `active/Agent.md` §三，本文件不抄 |

## 七、触发后首步动作

⭐ **直接按 Step1 派 qa（全新上下文），⛔ 不进 plan 模式、不先做别的。** Step1 → Step4 自动走完；只有铁律 2 的四种情形才在 Step5 停下问主人。
