# 🧱 前端形态与选型库（规划与执行共用，单一出处）

> **受众**：pm（推断端与形态、提议默认栈与家族）、uiux（写形态表与设计规格）、architect（落 `project.md` §一.1 家族契约）、dev / qa（按形态取驱动工具与视口）。各命令与角色正文只留指针，⛔ 不复述本文件。
> **一句话**：先定「有哪几端、每端什么形态」，再定「全项目一个组件库家族」，最后把设计数值灌进各端主题。
> **分工边界**：本文件只讲「怎么选、给多少算合适」；判词与规则号（VH / VM / VS）唯一出处 = `skills/cc-code/references/ui-gates.md`，⛔ 本文件不写规则号、不写阻断判据。
> **产物落点**：端与形态结论写 `prd.md` §〇 需求摘要（pm）；家族与各端版本写 `project.md` §一.1（architect）；页面与断点写 `ux.md` §一.1（uiux）；数值写 `design.md`（uiux）。

## 一、十种前端形态与第一版范围

| # | 形态 | 主设备 / 必测视口 | 第一版 | 关键特征 |
| :-- | :--- | :--- | :--- | :--- |
| 1 | 营销落地页 | 桌面 1440、移动 390 | ✅ 支持 | 对外获客、宣传、预约、下载、留资；首屏要放一个看得见的真实结果 |
| 2 | SaaS / Web App 生产力工具 | 桌面 1440、移动 390 可读 | ✅ 支持 | 登录后持续使用的工具界面；侧栏 + 工作台 + 数据 |
| 3 | B 端中后台 | 桌面 1440（纯内部工具可不做移动） | ✅ 支持 | 内部员工使用；表格、表单、审批、报表密集；通常无营销页 |
| 4 | 内容与文档门户 | 桌面 1440、移动 390 | ✅ 支持 | 文章、手册、帮助中心、API 文档；纯排版出格调 |
| 5 | 跨平台原生 App | 手机 390 | ⛔ 第一版不承诺 | 需要上架应用商店、调用原生能力；推断出须在需求摘要写后果请主人定 |
| 6 | 移动 H5 营销微站 | 手机 390 | ✅ 支持 | 微信内打开、分享卡片、扫码进入；一屏一动作 |
| 7 | 混合 App（壳内嵌 H5） | 手机 390 | ⚠️ 按移动 H5 支持 | 视觉只覆盖 H5 部分；壳层与原生能力不做视觉承诺 |
| 8 | 跨端编译小程序（Taro / uni-app） | 小程序视口，390 参考 | ⚠️ 只留驱动契约位 | 规则包推迟；界面驱动工具按端登记 |
| 9 | 原生小程序 | 小程序视口，390 参考 | ⚠️ 只留驱动契约位 | 同上 |
| 10 | 无前端 | — | ✅ 支持 | 纯接口 / 命令行 / 定时任务；`design.md` 状态写「不适用（无前端）」 |

```
第一版口径
  ├─ 完整支持 ── 网页 4 种（1 / 2 / 3 / 4）+ 移动 H5（6；7 按 6 处理）
  ├─ 只留契约位 ── 8 / 9（登记 wechat-devtools，规则与基线第一版不实施）
  ├─ 不承诺 ──── 5（qa 视觉段标「无法判定」，不得静默通过）
  └─ 无前端 ──── 10（全链路放行，design.md 标「不适用」）
```

> 一个项目可以有多个端（例如「网页营销落地页 + 移动 H5 + 小程序」），**每端一行**写进 `ux.md` §1.1；但全项目只允许一个组件库家族、只有一份 `design.md`。

## 二、pm 如何推断端与形态（不发问卷）

### 2.1 三者的关系

| 概念 | 是什么 | 谁定 | 落在哪 |
| :--- | :--- | :--- | :--- |
| 端 | 载体：网页 / 移动 H5 / 小程序 / 原生 App / 无前端 | pm 推断 | `prd.md` §〇 |
| 形态 | 该端属于十种里的哪一种 | pm 推断 | `prd.md` §〇；uiux 展开成 `ux.md` §1.1 |
| 家族 | 全项目唯一组件库家族 | pm 提议，architect 定契约 | `project.md` §一.1 |

### 2.2 推断判据（从主人产品雏形读信号，不发问卷）

| 主人雏形里的信号 | 推断结论 |
| :--- | :--- |
| 宣传、获客、预约、下载、留资、定价、案例 | 营销落地页（形态 1） |
| 登录后持续使用、工作台、订阅、协作、数据看板 | SaaS / Web App 生产力工具（形态 2） |
| 内部、员工、后台、管理、录入、审批、报表 | B 端中后台（形态 3） |
| 文档、手册、博客、帮助中心、API 说明 | 内容与文档门户（形态 4） |
| 微信内打开、分享卡片、扫码进入、一屏一动作 | 移动 H5 营销微站（形态 6） |
| 明确提到「小程序」 | 跨端编译小程序（形态 8）或原生小程序（形态 9），落地核实后二选一 |
| 上架应用商店、原生能力、离线、推送 | 跨平台原生 App（形态 5）→ 第一版不承诺，写后果请主人定 |
| 只有接口 / 命令行 / 定时任务 / 没有任何界面 | 无前端（形态 10） |
| 同一产品既有对外介绍又有登录后工具 | 多端：营销落地页 + SaaS 工具（两行） |

### 2.3 推断不出来的处理

```
 pm 读完主人雏形
   ├─ 能推断 ──► 写进 prd.md §〇：我替你选了（端 + 形态 + 推荐栈 + 推荐家族 + 理由）＋「想改就说」
   │              ⛔ 只写推荐与理由，不写版本号 / 主题入口 / 槽位名（那些归 project.md §一.1）
   ├─ 只能推断一半 ──► 先按最小合理组合提议，缺口在 §〇 明写「默认按 X，想改就说」
   └─ 真推不出（主人只说了一句概念，没有任何场景线索）──► 只问一句：
        「这东西主要给谁用：对外宣传、自己人天天用、还是只给内部员工录数据？」
        得到回答后立即落盘，⛔ 不连续追问、⛔ 不发问卷
```

> pm 在问答中可以画 ASCII 草图帮助确认，⛔ 草图不落盘；页面与原型归 uiux（`ux.md`）。

## 三、默认技术栈与组件库家族选择

### 3.1 默认技术栈

| 场景 | 默认栈 | 是否要问主人 |
| :--- | :--- | :--- |
| 网页类（营销 / SaaS / 后台 / 文档） | **React + Next.js** | 主人没要求就不问 |
| 纯内部重型后台、无营销页、只求快 | React + **Ant Design**（可改；不改就沿用默认 shadcn） | 不问，写进需求摘要 |
| 含小程序端 | React/Vue + 同时覆盖小程序与其余各端的家族（TDesign / NutUI / Ant Design 家族 / Vant，按端组合落地核实） | 只在家族覆盖不全时问 |
| 文档类 | Next.js 文档框架（如 Fumadocs，落地核实） | 不问 |
| 原生 App | 第一版不做 | 推断出就写后果请主人定 |

### 3.2 家族选择决策图

```
 端与形态已定（prd.md §〇）
   │
   ├─ 有「原生 App」端 ──────────────► 第一版不承诺：需求摘要写后果，请主人定
   │
   ├─ 有「小程序」端 ────────────────► 只在同时覆盖小程序 + 其余各端的家族里选
   │        ├─ 其余端含网页 ──► TDesign / Ant Design 家族（能覆盖网页 + 移动 + 小程序）
   │        ├─ 其余端只有移动 H5 ──► Vant / NutUI / TDesign（都能覆盖移动 H5 + 小程序）
   │        └─ 纯小程序 ──► Ant Design Mini / TDesign / NutUI / Vant Weapp
   │        以上一律先过 4.4 落地核实清单，再写进 project.md §一.1
   │
   ├─ 全体都是「纯内部重型后台」且无营销页、只求快 ──► 可改 Ant Design 家族；不改就按网页默认走 shadcn
   │
   ├─ 只有网页端（营销 / SaaS / 后台 / 文档）
   │        ├─ 文档类 ──► Next.js 文档框架（Fumadocs 落地核实）+ 网页底座
   │        └─ 其余 ────► shadcn 家族（默认）
   │
   ├─ 只有移动 H5 营销微站 ──────────► shadcn 家族（网页方案）或 Vant（若以后要扩小程序）
   │
   └─ 无前端 ───────────────────────► 不选家族；design.md 写「不适用（无前端）」

 选定后：
   ① 全项目一个家族，各端用家族对应版本
   ② 某端没有对应版本 → 需求摘要写清后果，请主人定（⛔ 不许混两个家族）
   ③ 家族与版本写进 project.md §一.1（唯一技术绑定值）
```

### 3.3 硬规则

| # | 规则 |
| :-- | :--- |
| 1 | 一个项目只用一个组件库家族；⛔ 不混家族、不混第二套图标、不混两套动画库 |
| 2 | 每端用该家族对应的版本；一端没有对应版本 = 换家族或请主人定，⛔ 不自行拼装 |
| 3 | 全项目一份 `design.md`；各端差异只写在 §九「各端主题映射」，⛔ 不按端拆第二份设计规格 |
| 4 | 家族、各端版本、主题入口、图标库、片段白名单与隔离目录，只在 `project.md` §一.1 写一次 |
| 5 | 明暗模式与界面语言按项目在 `ux.md` §1.1 登记；暗色要求与放行判据见 `ui-gates` |

## 五、三旋钮（版式变化 / 动效强度 / 信息密度）

> 三个名字沿用 taste-skill 原名，**按此顺序写**，例如「7/6/4」。⛔ 不得自造其他名字（如「表现力 / 留白节奏」）。

### 5.1 三个旋钮

| 旋钮 | 中文 | 管什么 | 写在 `design.md` §一 |
| :--- | :--- | :--- | :--- |
| `DESIGN_VARIANCE` | 版式变化 | 布局的对称度、偏移、不对称程度 | 第一个数字 |
| `MOTION_INTENSITY` | 动效强度 | 从「只做状态反馈」到「滚动编排」 | 第二个数字 |
| `VISUAL_DENSITY` | 信息密度 | 从大留白到驾驶舱 | 第三个数字 |

### 5.2 预设表（taste 原文 + 推算，标来源）

| 场景 | 版式变化 | 动效强度 | 信息密度 | 来源 |
| :--- | :---: | :---: | :---: | :--- |
| SaaS 营销落地页 | 7 | 6 | 4 | taste 原文 |
| Agency / 创意 | 9 | 8 | 3 | taste 原文 |
| 高端消费品牌 | 7 | 6 | 3 | taste 原文 |
| 设计师作品集 | 8 | 7 | 3 | taste 原文 |
| 开发者作品集 | 6 | 5 | 4 | taste 原文 |
| Editorial / Blog | 6 | 4 | 3 | taste 原文 |
| 公共部门 / 信任优先 | 3 | 2 | 5 | taste 原文 |
| Minimalist / Linear 风 | 5–6 | 3–4 | 2–3 | taste 原文 |
| SaaS 工具 | 4 | 3 | 6 | 推算（taste 不覆盖产品界面） |
| B 端中后台 | 3 | 2 | 7 | 推算 |
| 内容与文档 | 5 | 3 | 3 | Editorial 下调一档 |

### 5.3 档位含义与派生规则

| 旋钮 | 1–3 | 4–7 | 8–10 |
| :--- | :--- | :--- | :--- |
| 版式变化 | 对称居中 | 偏移 | 非对称 |
| 动效强度 | 仅 hover / active | 流式过渡 | 滚动编排 |
| 信息密度 | 大留白 | 日常 | 驾驶舱 |

| 派生规则 | 内容 |
| :--- | :--- |
| 移动塌单列 | 视口 < 768 一律塌成单列；断点变化写 `ux.md` §2.5 |
| 动效要真 | 动效强度 > 4 必须真的动起来，⛔ 不写「轻浮动」却静止 |
| 高密度禁通用卡 | 信息密度 > 7 时禁用通用卡片堆叠，数字用等宽数字 |
| 旋钮先于样板 | 旋钮值在 `design.md` 草稿阶段就定，风格样板板按它渲染 |

## 六、网站格调范式卡（4 种）

> 用法：uiux 按形态取对应一张作为起点，再按项目改；四张卡是「常见病与解法」，不是限制创意。

### 6.1 营销落地页

| 维度 | 内容 |
| :--- | :--- |
| 默认底座 | shadcn/ui + Motion |
| 配色家族 | 单色 + 单一点缀；或 Cobalt + Cream、Terracotta + Slate 等轮换 |
| 字体 | Geist、Satoshi、General Sans；中文 HarmonyOS Sans 或 MiSans |
| 中文排版 | 标题字距 0~0.02em、行高 1.3；正文行高 1.75 |
| 版式节奏 | 8 节至少 4 种布局族；节间距 112~160px；小标签 ≤ 节数 ÷ 3 |
| 动效 | 中：首屏入场 + 1~2 处滚动揭示 |
| 典型 AI 味（禁） | 紫蓝渐变、居中首屏、三等宽卡、方块拼假仪表盘、文字 logo 墙 |
| 高级感一招 | 首屏放一个看得见的真实结果 |
| 样板必含 | 首页、转化页、组件陈列 |
| 人判重点 | 换品牌测试、假截图、布局族不足、签名一招 |

### 6.2 SaaS / Web App 生产力工具

| 维度 | 内容 |
| :--- | :--- |

## 七、高级感正向标准

> 这是「往哪个方向使劲」的推荐值；是否阻断由 `ui-gates` 判。

| 维度 | 营销 / 品牌 | SaaS / 中后台 | 内容 / 文档 |

| 行长行高 | 英文 ≤ 65ch、1.5~1.65；中文 1.7~1.8；标题 1.05~1.2（中文 1.25~1.4） | 正文 20/14、表格行高 36~48 | 英文 65~75ch；中文每行 36~42 字、行高 1.8 |
| 字重 | ≥ 3 级，标题 500~600，英文大标题字距 -0.02~-0.04em | ≥ 3 级，层级靠字重和灰度 | 正文 400、标题 600 |

## 十二、主人原话 → 数值改动翻译表

> 诊断后**只改主题数值**，⛔ 不改单页；改完重新生成各端主题，再走视觉层。
> 本表是「听懂了该改哪个数」的翻译；规则判据仍在 `ui-gates`。

| 主人说 | 改什么 |
| :--- | :--- |
| 太廉价 | 阴影透明度降到 ≤ 0.08 并带色调，或改 1px 细线；强调色饱和度降 10~20 点；补 500 / 600 字重；圆角并成 1 套；换字体 |
| 像模板 / 像 AI 做的 | 换主色家族；换首屏布局族；小标签减到上限内；补签名一招 |
| 太素 | 展示字号比例提一档；加 1 张真实图；强调色面积 3% → 约 8% |
| 太花 / 太乱 | 强调色减到 1 个；去背景装饰；布局族收到 4~5 种 |
| 太挤 | 间距数值整体上调一档（如 96 → 128） |
| 太空 / 太散 | 信息密度旋钮 +2；节间距下调一档 |
| 太冷 / 太硬 | 中性色往暖偏 10~20°（全站统一）；圆角 4 → 8 |
| 看不清 | 正文对比度 ≥ 7 : 1；正文 +1px |

## 十三、主风格 skill：只许一个

| 项 | 规则 |
| :--- | :--- |
| 数量 | 一个项目只允许 **1 个主风格 skill**，在选择后登记进 `design.md` §一 |
| 默认主文件 | `design-taste-frontend`（taste 分支主文件） |

| 冲突怎么办 | 任何风格建议与规则冲突，一律以 `ui-gates` 为准 |

> 换主风格 skill = 换方向 = 回 `plan-uiux` 重走「定了」，⛔ 不带病混搭。
