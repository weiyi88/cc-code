# /cc-code:deploy — 上线编排器（一个命令，任意平台组合）

> **定位**：工作流最后一棒。只把**已验收通过**的代码发到线上、开通云资源、线上冒烟、留现状。
> **事实来源**：`active/project.md` §八 部署契约（组件 × 平台 × 密钥 × 健康检查）。命令只读契约，⛔ 不凭记忆猜平台。
> **平台知识**：`references/<平台>.md`，契约里用到哪个平台只读哪一份。加平台 = 加一份文档，⛔ 不加命令。

| 用法 | 场景 | 判据 |
| --- | --- | --- |
| `/cc-code:deploy` | 首次上线 | `gates.md` §八 目标环境行为空 → 走开通资源 |
| `/cc-code:deploy` | 日常发版 | §八 已有行 → 跳过开通 |
| `/cc-code:deploy rollback` | 线上出事 | 退回 §八「上一可用版本」 |
| `/cc-code:deploy <环境>` | 指定环境 | 缺省 = 生产 |

## 前置检查（任一不过即停，告诉主人缺什么、该走哪个命令）

| 检查 | 不过时 |
| --- | --- |
| 有 `.cc_code/active/` | 指路 `/cc-code:init` |
| `gates.md` §一 Verdict = PASS 且 §三 为空 | 指路 `/cc-code:agent-whole-qa` |
| 工作区干净（无未提交改动） | 列出文件，问主人是否提交；⛔ 不擅自提交 |

## 运行逻辑

```
 ① 读部署契约
     ├─ 齐全 ─────────────────────────────┐
     └─ 有缺项 / 整节空白                  │
          → 探测项目给草案，一次问一项      │
          → 切 Architect 写回 §八 → 复位 ──┤
                                           ▼
 ② 读平台文档（只读用到的）+ 查该平台最新官方文档校准命令
                                           ▼
 ③ 预检闸 ──任一不过──► 停，列缺口（缺代码适配 → 给出 just-do-it 一句话需求）
     │通过
     ▼
 ④ 首次上线？──是──► 列「待开通资源清单」→ 主人确认一次 → 逐个开通
     │否                                    │
     ◄──────────────────────────────────────┘
     ▼
 ⑤ 按依赖顺序发布（没有的组件跳过；危险动作逐条确认）
     数据库迁移 → 登录与回调 → 队列/存储 → 接口/Worker/定时 → 前端
     某组件失败 → 后续不再发，进 ⑥ 冒烟已发部分
     ▼
 ⑥ qa 独立线上冒烟（主控不自判）
     ├─ PASS → ⑦
     └─ FAIL → 报告人话结论 → 问主人是否回滚
     ▼
 ⑦ qa 就地更新 gates.md §八 → status.md 坐标 → milestone-log 一行 → 结束
```

### ① 读部署契约

- 读 `project.md` §八 四张表。缺项按 `plan-mvp` 同款纪律**一次只问一项**，⛔ 禁批量决策清单。
- 整节空白（老项目 / 规划时没填）：先探测项目给草案——依赖清单、平台配置文件（`vercel.json` / `wrangler.*` / `Dockerfile` / `docker-compose.*` / `supabase/`）、`.env.example` 的变量名——再逐项确认。
- 写回 §八 前把 `Agent.md`「当前激活角色」切 Architect，写完复位（同 plan-mvp）。

### ③ 预检闸（平台无关，四道全过才发）

| 闸 | 怎么判 |
| --- | --- |
| 平台已登录 | 每个用到的平台跑其文档「登录检查」 |
| 密钥齐 | §8.3 每个变量名在目标环境都已存在（只比名字，⛔ 不读值） |
| 回调已登记 | §8.4 每条回调都含正式域名——平台查不到的，请主人逐条确认 |
| 能构建能迁移 | 按生产配置本地构建通过；有数据库则迁移 dry-run 通过 |

### ⑤ 发布

- 每发完一个组件，记下平台返回的**版本标识**（部署 ID / Worker 版本 / 镜像 tag / 迁移版本），交 qa 写 §八。
- 首次开通产生的资源标识（库 ID、队列名、域名路由）允许写进**已存在的**平台配置文件，单独提交 `chore(deploy): ...`，提交前确认。

### ⑥ qa 冒烟（agent: qa）

| 项 | 内容 |
| --- | --- |
| 尺子 | §8.1 每个组件的健康检查 + 登录流程能走通 |
| 证据 | 健康检查实测结果 + 线上日志（按 project.md §七 去平台查发布后时段的 ERROR） |
| 输出 | Verdict（PASS / FAIL 清单）+ 就地更新 gates.md §八 |

### rollback 分支

```
 读 gates.md §八「上一可用版本」（逐组件版本标识）
     ▼
 列回滚清单 → 主人确认
     ▼
 逆序回滚：前端 → 接口/Worker → 队列 ……（数据库不回滚）
     ▼
 qa 冒烟 → 更新 §八 → 结束
```

> 数据库只向前（§八铁律）：平台回滚只回代码，库结构保持新版——所以迁移必须兼容上一版代码。

## ⛔ 铁律（本命令唯一规则源）

| 铁律 | 违反时 |
| --- | --- |
| 部署不改业务代码 | 平台要求改代码 / 加依赖 / 改运行时声明 → 停，给出 just-do-it 一句话需求或指路 plan-feature，验收后再来。唯一例外：上面「资源标识」那一条 |
| 密钥不进对话 | 不读值、不打印、不让主人贴；只经命令管道从 `.env` 文件 / 平台登录态传给平台命令行 |
| 危险动作逐条确认 | 推生产分支、生产迁移、改 DNS / 域名、删除资源、回滚，各自单独确认 |
| 未验收不上线 | 前置检查不过就停 |
| 冒烟不自判 | 只认 qa 的 Verdict |
| 命令以官方为准 | references 里的命令是参考；执行前查该平台最新官方文档（有 Context7 用 Context7，否则 WebFetch 官方站），冲突以官方为准 |

## 不碰

`prd.md` / `ux.md` / `data.md` / `api.md` / 业务代码。project.md 只写 §八。
