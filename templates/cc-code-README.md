# 🧭 .cc_code 使用手册（cc-code 1.13.0）

> 本文件由 `/cc-code:init` 生成并随插件版本刷新，是**给「不熟悉 cc-code 的人」的上手说明书**。
> 项目业务状态永远在 `active/`；本手册只讲「这套系统怎么用」。

---

## 一、这套系统在解决什么问题

LLM 写代码有三病：**写着写着忘了目标、上下文越滚越脏、凭记忆瞎答**。
cc-code 的处方：**把记忆、状态、规则全部外部寄存到 `.cc_code/` 静态文件**，AI 每次会话按协议读文件定位自己，而不是靠脑容量。

```
① 记忆/逻辑/状态全外部寄存 ── 落 .cc_code/ 静态文件
② 责任垂直化 ── 每个 agent 只掌一层，禁止越权
③ 决策串行 ── pm → architect → dev → qa，一次只派一个 agent
```

---

## 二、核心逻辑：agent 串行 + 文件分层

### 角色 = agent（主控只传话）

```
pm ──► uiux ──► architect ──► dev ──► qa
(需求)  (交互+长相)  (契约)      (编码)   (验收)

旁路：curator（结算后静默整理经验）
风格改版：agent-uiux（只接「已定未实现」，不派 uiux；uiux 只在规划侧出场）

主控 = 编排者：派 agent、原样转问、原样续接你的回答；
         不读代码、不替你回答、不代写任何角色的文件（含 init 升级迁移，要改一律派该文件的写者 agent），只记坐标（`status.md`）与里程碑（`backup/milestone-log.md`）
```

派哪个 agent，它就是哪个角色，没有「切角色」这一步。每个 agent 只许按自己的权限卡片读写文件（卡片只在 `active/Agent.md` §三 写一次），越权即违规。

- **uiux 写两份**：`ux.md`（交互与布局：形态表 / 页面清单 / ASCII 原型 / testid / 五态 / 断点 / 流转）与 `design.md`（风格与长相：色彩 / 字体 / 间距栅格 / 形状深度 / 动效 / 组件长相 / 各端主题映射 / 页面构图）。判据一句话：**换一套皮肤仍然成立 → `ux.md`；换皮肤就会变 → `design.md`**。
- **uiux 不写项目代码**，只在 `plan-mvp` / `plan-feature` / `plan-uiux` 出场；`agent-*` 命令里没有它。

> **串行 ≠ 单线程（1.6.0）**：`project.md` §九 把一个阶段拆成几条互不相干的泳道后，执行时同一角色可以多人同时干（Dev 一起写 → 全部写完 → QA 一起验 → 没过的泳道单独退回）。agent 顺序不变，每个文件仍只有一个写者。没写泳道就照旧单线程。

### 文件分层（先认层，再认谁写）

| 层 | 文件 | 装什么 |
| --- | --- | --- |
| **L0 控制** | `active/Agent.md` | 最高宪法：agent 分工 + 权限卡片 |
| | `active/status.md` | 当前坐标 + 卡点 + 下一步（含「风格：」坐标行；里程碑不落此文件） |
| **L1 意图** | `active/prd.md` | 分模块业务逻辑 + 规则 + 验收断言 A1..An + §〇 需求摘要（端与形态、默认栈与家族） |
| **L2 表现** | `active/ux.md` | 交互与布局：前端形态表 / 页面清单 / ASCII 原型 / 元素 testid / 五态矩阵 / 断点 / 流转（uiux） |
| | `active/design.md` | 风格与长相：色彩 / 字体排版 / 间距栅格 / 形状深度 / 动效 / 图标图像 / 组件长相 / 各端主题映射 / 页面构图（uiux） |
| **L3 实现** | `active/project.md` | 技术宪法（架构 / 选型 / `§一.1` 组件库家族 / `§六` 测试与视觉基建 / `§八` 部署 / `§九` 阶段与泳道） |
| | `active/data.md` | 数据契约（interface ↔ DB 列） |
| | `active/api.md` | 接口契约（method/path/入参/出参/错误码） |
| **L4 验收** | `active/gates.md` | QA 实测结果 + FAIL 清单 + `§2.4` 视觉段（A + U + V；dev 禁读） |
| — | `active/bugs.md` | 未修复 bug 工作上下文（B-n 施工便签，修完搬走） |
| — | `.cc_code/design/` | 方向卡、风格样板板与截图（uiux 写，**不是项目代码**，入 git） |
| — | `.cc_code/test/visual/` | 视觉机器检查测试（qa 写，入 git）；`baseline/` 为截图基线（qa 独占，入 git） |
| — | `references/` | 项目级经验库（curator 全自动整理；INDEX 索引，architect / dev 按需读）。个人库 `~/.cc-code/lessons/`、团队库 `~/.cc-code/team/` 在项目外；主题文件写法范本见插件 `templates/references-example-async-queue.md` |
| — | `docs/qa/` | QA 全量报告 + 合集板 + 证据产物 |
| — | `backup/` | 冷数据归档：change-log.md / milestone-log.md / `retired/` 退役原文（人看历史，AI 工作时禁读） |
| — | `.cc_code_version` | 场域版本戳 |

> 谁写哪个文件、各 agent 的读写范围，单一出处 = `active/Agent.md` §二 / §三，此处不抄副本。`Agent.md` 与根目录 `CLAUDE.md` / `AGENTS.md` 是插件规范文件，唯一写者 = init 脚本（升级时机械覆盖，旧版先快照），项目内不手改。
> 旧项目根目录的 `design.pen` 原地保留：**不读、不写、不转换**，不再是视觉事实源；视觉事实源是 `active/design.md`。

**信息流单向**：`L1 → L2（ux.md 交互布局 + design.md 设计规格）→ L3 → 代码 → L4 回验`。L4 只拿 L1/L2 当尺子，绝不拿代码当尺子。
**V 刻度的来源**：视觉判词（V 行）的尺子 = `design.md` 的数值 + 插件规则库 `ui-gates.md` 的阈值；V 编号发号处 = `gates.md` §2.4 V 段（页章号 + 组码）。

### active 为什么不会越用越胖（1.7.0）

`active/` 只放**项目最新的状态和内容**。任何 agent 写它之前，先按下面处置一遍：

```
          要写 active 文件
                 │
    ┌────────────┼──────────────┬────────────────┐
    ▼            ▼              ▼                ▼
 内容变了     内容是新的      内容过期了        内容没变
                            (做完/修好/作废)
    │            │              │                │
    ▼            ▼              ▼                ▼
只改那几行   插进它该在的    原文整段搬进        一行不碰
其余不动     小节, 不堆末尾  backup/retired/
                            再从 active 移除
    │            │              │                │
    └────────────┴──────┬───────┴────────────────┘
                        ▼
   active 只剩最新状态　旧内容在 backup 全文可查　一个字都没丢
```

| 好处 | 怎么来的 |
| --- | --- |
| 文件不随对话次数变胖 | 过期内容每次都搬走，active 行数由「现在有多少规则」决定，不由「用了多少次」决定 |
| 省钱、不丢缓存 | 没变的行一次都不重写 |
| 旧内容照样查得到 | 全在 `backup/retired/<源文件名>.md`，一字不丢；`backup/` 不进 git，不怕大 |

> ⚠️ `backup/` 是历史的唯一载体且不进 git —— 别手动清它。

### 前端长什么样，怎么定（1.11.0）

前端不再靠「口头说好看」：全项目**一份设计规格**（`active/design.md`）+ 一套可判的视觉规则，谁也改不了口。

```
 规划期（人参与）                        执行期（纯机器）
 ─────────────                        ─────────────
 pm 推断端与形态 + 默认栈/家族           视觉地基：dev 搭主题 + 全局框架 + 组件陈列页（不上线）
        │                                     │
 uiux 写 ux.md（行为/布局）                 qa 复核 + 首次冻结截图基线
        │                                     │
 plan-uiux 定风格 → 主人「定了」           后续阶段：页面只引用主题数值、只用一个家族
        │                                     │
 design.md 锁定                          qa 开发后检查 → V 段 + 合集板
```

| 事项 | 口径 |
| --- | --- |
| 十种前端形态 | 营销落地页 / SaaS 工具 / B 端中后台 / 内容与文档 / 跨平台原生 App / 移动 H5 微站 / 混合 App / 跨端编译小程序 / 原生小程序 / 无前端。pm 从你的产品雏形**推断**，不发问卷；结论写 `prd.md` §〇 |
| 默认技术栈 | React + Next.js（你没要求就不问）；第一版只承诺网页四种 + 移动 H5；原生 App 不承诺，小程序只留契约位 |
| 一个组件库家族 | 全项目只用一个家族，各端用家族对应版本（如 shadcn / Ant Design / TDesign）；没有家族能覆盖全部端 → pm 在 §〇 说明后果请你定 |
| 一份设计规格 | `design.md` 灌进各端主题入口；dev 生成的主题文件是**生成物，禁手改**——要改数值 → 改 `design.md` → 重新生成 |
| 两个模式 | `plan-uiux` **模式一 定风格**（新项目）、**模式二 改版**（已上线界面要改长相，qa 先出现状体检） |
| 三道门 | ① 开工视觉门：本阶段涉及页面而 `design.md` 未锁 → 执行器拒跑，指路 `plan-uiux`；纯后端阶段放行标「不适用」<br>② 唯一视觉门：你亲口说「定了」，`design.md` 才锁定<br>③ 基线门：qa 通过后冻结截图基线；失败轮禁止冻结 |
| 检查时机 | 现状体检（qa，模式二）／锁定前（uiux 自检 + 视觉地基 qa 复核）／开发后（qa，各执行命令）—— 三个时机的判据与规则号见插件 `skills/cc-code/references/ui-gates.md` |
| 基线归属 | 截图基线 `.cc_code/test/visual/baseline/` 与允许值集合：**qa 独占写、入 git**；⛔ 不许全局忽略截图 |
| 视觉地基 | `agent-mvp` 第一阶段固定：主题入口 + 全局框架 + 组件陈列页（项目里的**不上线路由**，逐项展示组件全部状态）；业务页面排在它之后 |
| 合集板 | qa 把只能人看的审美问题（VS）汇总到 `.cc_code/docs/qa/` 的合集板给你看；**不卡流程、不进分母** |
| 双屏宽冒烟 | `deploy` 上线后 qa 在 **390 / 1440** 各截首页 + 一页主流程，并在同页同屏宽采样性能；只作证据，不新增阈值 |

> 你说「太廉价 / 太花 / 太挤 / 像模板」这类人话时，uiux 会按插件 `frontend-forms.md` 的翻译表**只改主题数值**，不逐页重画；改完再走一次「定了」。
> 规则唯一出处：判词与阈值 = `skills/cc-code/references/ui-gates.md`；形态、默认栈、家族、三旋钮、片段五步 = `skills/cc-code/references/frontend-forms.md`。

| skill | 触发 | 什么时候用 |
| --- | --- | --- |
| `init` | `/cc-code:init` | 首次使用建好整个管理文件夹和核心文档；已有项目自动升级，全程零删除 |
| `cc-code` | 自动 | 含 `.cc_code/` 的项目自动加载的流程管家：规划→开发→测试→验收，四步走完才准上线 |
| `plan-mvp` | `/cc-code:plan-mvp` | 做新项目：pm 逐条问清需求并推断端与形态（不发问卷），uiux 写页面原型；【需求与原型批准】后 architect 问技术方案，【技术批准】后落盘 |
| `plan-feature` | `/cc-code:plan-feature` | 加新功能：pm→uiux→architect 查冲突；新页版式两档（只用已锁数值免门但要登记；引入新数值/组件/母题回 `plan-uiux`） |

| `agent-uiux` | `/cc-code:agent-uiux` | 把「风格已定未实现」落进代码：dev 重新生成主题、调长相与布局；qa 全量五态回归 + 全页视觉 + 基线对比（≤3 轮） |
| `agent-feature` | `/cc-code:agent-feature` | 只写新功能涉及的代码，只跑相关测试，又快又稳 |
| `agent-whole-qa` | `/cc-code:agent-whole-qa` | 上线前开浏览器把每个页面每个按钮全点一遍（含视觉第四层），FAIL 自动修 |
| `plan-debug` | `/cc-code:plan-debug` | 出 bug 后先由 QA 复现取证并当场记进 bugs.md，再由工程师只读查到根因，记录自动整理、不等你批准；只在需要你拍板时才停下问你 |
| `agent-debug` | `/cc-code:agent-debug` | 按修复方案改代码，跑相关测试全绿才算修好（视觉 bug 同样走这里） |
| `short` | `/cc-code:short` | 简单问题只回一句话（≤50 字），绝不啰嗦 |
| `just-do-it` | `/cc-code:just-do-it` | 小改动一句话就干：dev 写完 qa 验，记一笔就完事；命中前端文件只做静态扫描、只记录 |

| `pr` | `/cc-code:pr` | 项目走外部审查平台时用：验收通过后点一下，自动规范提交、推送功能分支、带描述建合并请求；被打回照常走 debug / feature |

## 四、使用方案：两条路线

> **1.13.0 起 plan 批准后自动开工**：你批准规划（定风格时说「定了」）后，对应的执行命令会自己接着跑，不用再敲。下面路线里标「自动」的步骤就是这样接上的；想停下随时按 Esc。上线（`deploy`）与交付（`pr`）仍只能你自己敲。

### 路线 A：全新项目（0 → MVP）

```
/cc-code:init            ← ① 搭场域（1 分钟；新建即建好设计目录与截图基线目录）
/cc-code:plan-mvp        ← ② pm 问清需求并替你定好端/形态/默认栈与家族 → uiux 画页面原型
                              →【批准一：需求与原型】→ architect 问技术方案 →【批准二：技术方案】→ 落盘
                              （无前端 → 自动接 ④）
/cc-code:plan-uiux       ← ③（有前端）定风格：方向卡（营销/品牌类且你没给方向时才给）
                              → design.md 草稿 → 风格样板板 → 你说「定了」→ 锁定 → 自动接 ④
（自动）agent-mvp         ← ④ 纯执行：首阶段视觉地基（主题 + 全局框架 + 组件陈列页，不上线），
                              之后业务页面只引用主题数值；Dev→QA 到收口
/cc-code:agent-whole-qa  ← ⑤ 全量验收（功能 + 五态 + 元素 + 接口 + 视觉，含合集板）
```

### 路线 B：MVP 已交付，加新功能

```
/cc-code:plan-feature  ← ① 增量规划：pm→uiux→architect；新页版式两档
                          （只用已锁数值免门但要登记；引入新数值/组件/母题 → 先回 plan-uiux）
（自动）agent-feature   ← ② 批准后自动接：增量纯执行：定位 → Dev→QA（精准回归）
```

### 路线 C：修 bug（需求明确，只是实现错了）

```
/cc-code:plan-debug        ← ① 诊断（qa 复现取证并当场写 B-n 到 active/bugs.md
                               → dev 只读查根因 → qa 补全；不等你批准，
                               只在契约错/需求错/视觉规格错/找不到期望/复现不了时问你一句）
（自动）agent-debug         ← ② 进入「待修复」后自动接：修复纯执行：定位 B-n → Dev→QA
                               （B-n 用例 + affected 精准回归 + 回归测试留守；视觉 bug 同链）
```

### 路线 D：已上线界面要改长相（需求不变）

```
/cc-code:plan-uiux     ← ① 模式二 改版：qa 现状体检 → uiux 写目标 design.md
                           → 改前改后对照样板板 → 你说「定了」→ status 标「已定未实现」
（自动）agent-uiux      ← ② 「定了」后自动接：dev 重生成主题 + 调长相与布局；qa 全量五态回归 + 全页视觉 + 基线对比
                          （碰流转 / 五态 / 接口就停下交你；功能与长相都改 → 先做本命令，再走 agent-feature）
```

**何时走哪条线（决策表）**：

| 你的情况 | 走 | 不走 |
| --- | --- | --- |
| 需求模糊，要新增/改动功能 | 路线 B（plan-feature） | debug 链（bug 不发明需求） |
| 行为错了，期望行为说得清（或有既有断言） | 路线 C（plan-debug） | 路线 B（别用 30 分钟需求仪式修 bug） |
| 修复需要改契约/改需求 | 先走路线 C 诊断；根因落在契约/需求上时会停下问你，你裁决后由架构/产品 agent 改文档，再修 | 别绕开诊断直接走路线 B |
| 需求不变，只是页面不好看 / 想换风格 | 路线 D（plan-uiux 模式二 → agent-uiux） | 路线 B（长相不是新需求）；直接手改主题生成物（会被重新生成覆盖） |

### 任意时刻

```
/cc-code:init                ← 插件升级后再跑一次，自动迁移场域（零删除）
```

## 五、使用示例

### 示例 1：第一次用，项目已有代码

```
你：/cc-code:init
AI：检测到旧项目（Track A）→ 备份旧 CLAUDE.md → 搭场域 → 请你补需求
```

## 六、references 经验库怎么用

经验由 **curator** 在每次执行器结算后后台静默整理，你零操作；它是所有经验库的唯一写者，qa 只在验收矩阵上做标记。

```
执行器结算 → 主控后台派 curator → 三道筛（连续/回归 → 实现缺陷或设计遗漏 → 证据齐）
          → 分级（项目 / 个人）→ 追加进主题文件 → 重建 INDEX → 最终报告多一行结果（无变化不写）
漏派 → 唯一的 Stop hook 只比时间戳，提醒主控补派
```

| 级别 | 位置 | 说明 |
| --- | --- | --- |
| 项目 | `.cc_code/references/` | 跟项目走；architect / dev 读 |
| 个人 | `~/.cc-code/lessons/` | 跟人走；curator 写，architect 读，经 architect 转写进 `project.md` §五 才影响开发 |
| 团队 | `~/.cc-code/team/<仓库名>/` | 只读；把 git 地址发给 AI 并说明是团队经验，由 curator 克隆 |

- **渐进式披露**：每级一个 `INDEX.md`（每个主题一行：主题、何时读、有效条数、休眠条目）+ 按主题的资料文件（如 `async-queue.md`）+ `archive/`。读的人先扫 INDEX，命中主题才打开，未命中一个都不读，零负担。
- **条目五字段**：背景、输入、输出、发生什么、约束；不写断言编号、数值、密钥、客户名、内部地址、代码。
- **只追加**：不覆盖不删除；7 个活跃日未被采纳 → 休眠（读者可跳过，被采纳即恢复）；14 个活跃日未被采纳或被报告「不适用」→ 归档到 `archive/`，原文保留。
- **谁读**：architect（规划阶段首次派出时）读三处 INDEX；dev 读项目 INDEX；qa / pm / uiux 不读。完成报告里的「采纳经验」一行就是采纳记录。
- **优先级**：active 文件 ＞ 项目 ＞ 个人 ＞ 团队；经验只当自检问题，不当验收尺子。
- **没有手动入口**：经验只从验收里真实发生过、已修好的错自动整理，你什么都不用做。

## 七、常见疑问

| 疑问 | 答案 |
| --- | --- |
| 我要手动切角色吗？ | 不用。角色就是被派出的 agent，命令会按顺序派；`Agent.md` 里没有「当前角色」字段 |
| AI 会自己乱改需求吗？ | 权限卡片禁止：dev / qa 禁改 prd / ux / design / api；改不动就上报，由主控交你裁决 |
| 我能直接改 `Agent.md` / `CLAUDE.md` 吗？ | 不用也不建议：它们是插件规范文件，只有 init 脚本写，升级时会整份覆盖（旧版有快照）。项目自己的约定写进 `project.md` 的「特殊约束」，由 architect 写 |
| 旧版场域升级会丢东西吗？ | 不会。全程零删除，旧物只 cp 快照与 mv 归位，永远可回溯 |
| **前端风格谁定？我想换风格怎么办？** | 风格由 `plan-uiux` 定，**只有你说「定了」才锁定**。想换：新项目说方向或重跑 `plan-uiux`；已上线界面走 `plan-uiux` 模式二改版 → `agent-uiux` 落地。锁定后改数值只能经 `plan-uiux` |
| **老项目没有 `design.md` 怎么办？** | 首次执行可走**一次性的冷启动豁免**（执行器按三条件发放，只放行存量未改页面）；建议先跑 `plan-uiux` 补锁，豁免不重复发 |
| **页面看着不齐 / 像 AI 做的，怎么让 AI 重做？** | 用人的话说清哪里不对（太廉价 / 太花 / 太挤 / 像模板）→ `plan-uiux` 模式二按翻译表**只改主题数值**并出对照样板板 → 你说「定了」→ `agent-uiux` 落地；不逐页重画 |
| 验收标准在哪？ | `prd.md` §1.5 断言 A1..An + `ux.md` §2.3 五态 U 编号 + `design.md` 的视觉数值（编号永久稳定、永不复用；作废条目搬进 `backup/retired/`，active 里不留） |
| 实测结果在哪？ | `gates.md`（A + U + V 追溯矩阵；QA 写，Dev 禁读 —— 防拿答案做题） |
